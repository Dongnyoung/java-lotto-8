# 로또

로또 게임 애플리케이션은 사용자로부터 **구입 금액**, **당첨 번호**, **보너스 번호**를 입력받아  
로또 번호를 자동 발행하고, **당첨 내역 및 수익률을 출력**하는 프로그램입니다.

본 프로젝트는 **입력 / 도메인 / 출력** 책임을 명확히 분리하고,  
각 기능을 **클래스 단위로 구현하는 것**에 초점을 두었습니다.

---

## 기능 요구사항 정리

### 1. 구입 금액 입력
- 숫자가 아닌 입력 예외 처리
- 1,000원 단위만 허용
- 구매 가능한 로또 **장 수 계산**

### 2. 로또 번호 발행
- `1 ~ 45` 범위 내 **중복 없는 숫자 6개**
- 발행 개수 = `구입 금액 / 1000`

### 3. 당첨 번호 입력
- 쉼표(`,`) 기준 파싱
- 6개 숫자 입력
- 숫자 범위 예외 처리

### 4. 보너스 번호 입력
- 당첨 번호와 **중복 불가**

### 5. 당첨 결과 계산
6개 번호 일치 개수와 보너스 번호 일치 여부에 따라 등수 결정

| 등수 | 조건 | 상금 |
|-----|------|------|
| 1등 | 6개 일치 | 2,000,000,000원 |
| 2등 | 5개 + 보너스 일치 | 30,000,000원 |
| 3등 | 5개 일치 | 1,500,000원 |
| 4등 | 4개 일치 | 50,000원 |
| 5등 | 3개 일치 | 5,000원 |

### 6. 결과 출력
- 등수별 당첨 개수 출력
- 총 수익률 계산 및 출력

## 클래스 구성

| 클래스 | 역할 |
|-------|------|
| **LottoController** | 전체 흐름 제어 (입력 → 계산 → 출력) |
| **CostInput** | 구입 금액 입력 |
| **Cost** | 금액 검증 및 티켓 수 계산 |
| **LottoInput** | 당첨 번호 입력 |
| **Lotto** | 당첨 번호 보관 및 검증 |
| **BonusInput** | 보너스 번호 입력 |
| **BonusNumber** | 보너스 번호 검증 |
| **LottoTickets** | 로또 번호 자동 발행 |
| **WinningMap** | 당첨 결과 카운팅 관리 |
| **LottoResultMapper** | Map → 결과 모델 리스트 변환 |
| **LottoResult** | 등수/당첨 개수/상금 데이터 모델 |
| **ResultOutput** | 결과 출력 |

##  전체 흐름 및 클래스 구조

### 1) 전체 흐름
1. CostInput으로 입력을 받고 Cost클래스에 넘겨주어서 입력값 검증을 받음 
2. 로또 티켓 장수를 받아서 장수만큼 로또번호(7자리)를 발행함 이걸 userNumbers에 저장
3. 당첨번호 사용자로부터 입력을 받아서 winningLottoNumbersList에 받음 
4. BonusInput으로 보너스 번호 입력 받고 BonusNumber에 입력값을 넘겨주며 입력값 검증을 받음 
5. 보너스 번호를 저장 
6. WinningMap을 이용하여 당첨 확인 
7. 당첨 통계를 내기위해 LottoResultMapper 이용하여 results에 저장 
8. ResultOutput을 이용하여 결과를 출력

## 테스트 & TDD 기록

이번 과제에서는 **도메인 로직을 우선 검증**하는 방향으로 테스트를 충분히 작성하였고,
향후 과제에서는 **TDD 사이클(RED → GREEN → REFACTOR)** 로 확대 적용해볼 계획이다.

### 테스트 전략

- **단위(Unit) + 기능**
  - 핵심 비즈니스 규칙은 **단위 테스트**로 빠르고 촘촘하게 검증
  - 전체 흐름은 **기능테스트**로 입력→도메인→출력까지 보장

- **도메인 순수성 유지**
  - `domain` 계층에서 `System.out.println`, 콘솔 입출력 의존 제거
  - 불변(immutable) 값 객체 중심으로 설계

### 작성된 주요 테스트

- **통합/기능 테스트**
  - `lotto.ApplicationTest`
    - 콘솔 입출력 흐름을 포함한 **엔드투엔드 시나리오** 검증
    - `assertRandomUniqueNumbersInRangeTest`로 **발행 번호 시퀀스 고정**하여 재현성 보장
- **도메인 기능 스타일 테스트 (단위에 가까운 종합)**
  - `domain.WinningMapFeatureTest`
    - 실제 티켓 묶음을 입력해 **등수별 카운트 + 총 상금**을 한 번에 검증
    - 과제에서 요구하는 결과 표/수익률 계산을 **도메인 레벨**에서 확인
- **도메인 단위 테스트**
  - `domain.WinningMapTest`
    - 3/4/5/5+보너스/6 등수 로직, 3개 미만 등 검증

### TDD 적용 메모

- 이번 과제에서는 일부 기능에서 **코드 후 테스트 보강**도 있었기에, TDD는 아니다.
- 다만, 테스트를 기준으로 설계를 정리하고(`전략 분리`, `도메인 순수화`.. 등),
  **다음 기능부터는 테스트를 먼저 작성하는 TDD 사이클**을 적용할 수 있는 구조를 갖추도록 노력 해야겠다.

## 설계 회고

- 처음부터 객체지향적으로 나누려 했지만, **구현 → 리팩토링** 흐름이 더 효율적이었다.
- 단순히 실행되는 것에 대한 테스트가 아닌 정말 테스트 다운 테스트를 하기 위해 고민하였다.
- 입력/출력/도메인 로직 분리로 **유지보수성과 테스트 용이성이 향상**되었다.
- 입력(CostInput, LottoInput .. 등)과 도메인(Cost,Lotto .. 등)으로 나눈건 입력은 바뀌고 도메인은 바뀌지 말아야할 것이라고 생각하였기 때문이다.
  - 예를 들어, 금액 입력은 `CostInput`이 문자열을 입력받고,  
  의미 있는 금액인지 판단하는 검증은 `Cost` 도메인 객체에서 수행한다.
  - 이를 통해 입력 방식(콘솔 -> 웹/앱) 변경 시 도메인 유지, 도메인 테스트가 순수하고 독립적으로 가능
  - 책임과 계층 의도가 명확하게 드러나는 구조를 확보할 수 있었다.
- `WinningMap` + `LottoResultMapper` 조합으로 **당첨 카운트와 출력 모양을 분리**할 수 있었던 점이 좋았다.
